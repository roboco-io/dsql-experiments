## 결과 요약

이 실험은 같은 주문 업무를 같은 지연 목표(SLO)로 실행할 때 DSQL이 대조군보다 얼마나 많은 요청을 처리하고 지연이 어떻게 다른지 확인하려 했습니다. 업무는 상품 조회 40%, 주문 이력 조회 30%, 주문 생성 20%, 주문 취소 10%로 섞었고, SLO는 읽기 p95 50 ms·p99 100 ms, 쓰기 p95 100 ms·p99 200 ms입니다. 계획한 본 측정까지는 마치지 못했으므로 이 보고서는 **부분 결과**입니다.

요청을 정해진 도착률로 보내는 방식(open-loop)의 파일럿에서 DSQL(D1)과 Aurora Serverless v2(A2)는 100, 400, 1600 TPS 모두 SLO를 통과했고, 실패와 업무 불변식 위반은 0건이었습니다. DSQL의 지연은 부하가 16배 늘어도 거의 변하지 않았습니다(1600 TPS에서 주문 생성 p95 41.0 ms, 상품 조회 p95 9.1 ms). 다만 같은 1600 TPS에서 Serverless v2의 주문 생성 p95는 6.8 ms여서, DSQL의 쓰기 지연은 약 6배 길었습니다. DSQL은 퍼블릭 엔드포인트라 네트워크 왕복 시간(RTT)도 2.7–5.1 ms로 대조군(0.1–0.7 ms)보다 길었는데, 이 차이만으로는 쓰기 지연 차이를 설명하지 못합니다.

연결 수를 고정하고 쉬지 않고 요청을 보내는 방식(closed-loop)으로 최대 처리량을 찾는 탐색에서, 연결 16개일 때 DSQL은 1,006 TPS, RDS Multi-AZ(R1)는 3,065 TPS, Aurora Provisioned(A1)는 3,375 TPS, Serverless v2는 5,657 TPS였습니다. 연결 하나가 요청을 하나씩 처리하므로 이 값은 요청 지연에 반비례하며, DSQL의 용량 한계가 아니라 긴 지연의 결과입니다. 대조군이 SLO를 지킨 최고 처리량은 R1 5,839 TPS, A1 3,375 TPS, A2 11,559 TPS였습니다. DSQL은 셀마다 실행하는 초기화(셀이 만든 행 수십만 개 삭제)가 너무 느려 연결 64 셀이 두 번 제한 시간을 넘겼고, 예산 상한에도 닿아 **DSQL의 SLO 용량과 기준 처리량(Qref)은 측정하지 못했습니다**. Spot 러너 회수가 두 차례 있었고, 러너 사양이 파일럿(`c7g.4xlarge`)과 탐색(`c6g.4xlarge`)에서 다릅니다. 하네스 추정 비용은 약 USD 53이며 실제 청구액은 확인 전입니다.

### 프로덕션 사용 관점

DSQL은 1,600 TPS까지 지연 목표를 여유 있게 지켰고(쓰기 p95 약 41 ms, 읽기 약 10 ms) 오류와 정합성 위반도 없었으므로, 이 정도 부하의 OLTP에는 쓸 수 있다고 봅니다. 다만 쓰기 지연이 Aurora Serverless v2보다 약 6배 길어, 연결 16개로 낸 처리량이 약 1,000 TPS로 대조군의 1/3–1/6이었습니다. 같은 처리량을 내려면 애플리케이션의 연결 수와 동시성을 더 늘려야 합니다. 대량 삭제·정리 작업은 매우 느렸고, 비동기 인덱스와 트랜잭션 크기·시간 제한에 맞춘 작업 분할이 필요했습니다. DSQL의 최대 용량은 이번에 측정하지 못했으므로, 1,600 TPS를 넘는 부하에 대한 판단은 재측정 뒤로 미룹니다.

## 확인할 질문

DSQL의 SLO 용량·지연은 각 대조군의 몇 배인가?

이번 실행으로는 지연 비교(1600 TPS까지)와 연결 16개 기준 처리량 비교까지만 답할 수 있습니다. SLO 용량 비율은 재측정 과제로 [이슈 #2](https://github.com/roboco-io/rds-experiments/issues/2)에 남겨 두었습니다.

## 실행 조건

- **리전과 일시:** 서울(ap-northeast-2), 2026-09-28 03:34–12:07 UTC.
- **구성:**
  - D1: Aurora DSQL 단일 리전, IAM 토큰 인증, 퍼블릭 엔드포인트.
  - R1: RDS for PostgreSQL 16, `db.r6g.xlarge` Multi-AZ, gp3 400 GiB.
  - A1: Aurora PostgreSQL 16 Provisioned, `db.r6g.xlarge` writer 1 + 다른 AZ reader 1, Aurora Standard.
  - A2: Aurora PostgreSQL 16 Serverless v2, writer 1 + reader 1, 각 4–32 ACU, Aurora Standard.
- **데이터:** 고객 100만, 상품 20만, 주문 1,100만, 주문 품목 2,750만, 원장 1,100만 행(약 5 GiB). D1의 적재 행 수는 DB에서 직접 세어 설계값과 일치함을 확인했습니다.
- **업무와 판정:** 위 혼합 업무, 명시적 `REPEATABLE READ`, 재시도 정책 공통. 기술적 실패율 0.1% 이하와 SLO를 모두 지켜야 통과입니다. 셀마다 재고·주문·원장 불변식을 검사했습니다.
- **부하 발생기:** 구성마다 Spot 러너 1대. 파일럿은 `c7g.4xlarge`, 탐색은 Spot 용량 부족과 회수로 네 구성 모두 `c6g.4xlarge`를 썼습니다. 발생기 CPU는 최대 69.7%(A2 연결 256)로 포화 기준(85%) 아래였습니다.
- **셀 시간:** 파일럿 워밍업 60 s + 측정 120 s, 탐색 워밍업 120 s + 측정 300 s, 각 1회.
- **계획과 달라진 점:**
  - 본 측정(0.5/1.0/1.2 × Qref)과 경계 탐색은 실행하지 못했습니다.
  - 비용 상한을 USD 50에서 60으로 올렸습니다(2026-09-28 사용자 결정).
  - DSQL 탐색은 연결 16만 결과가 있습니다.

## 개발·운영 편의성

- **대량 삭제가 느림:** 셀이 만든 행을 되돌리는 초기화에서, D1은 약 13만 건의 영수증과 관련 행(주문·품목·원장·재고 복원 합계 약 60만 행 변경)을 처리하는 데 6–7분이 걸렸습니다. 처음 구현은 배치마다 대상 조회를 다시 실행해 27분 제한을 넘겼고, 대상을 한 번만 조회하도록 고친 뒤에도 연결 64 셀의 초기화는 제한 시간 안에 끝나지 않았습니다. 대조군은 같은 초기화가 셀 시간에 문제를 주지 않았습니다.
- **외래 키 역방향 인덱스:** 주문을 지울 때 원장의 `order_id`에 인덱스가 없어 매 삭제가 원장 전체를 훑었고, D1은 트랜잭션 300초 한도(`ProgramLimitExceeded`)에 걸렸습니다. 이 문제는 A2에서도 24분 걸린 삭제로 나타났습니다. 인덱스를 추가해 해결했습니다.
- **비동기 인덱스:** DSQL의 `CREATE INDEX ASYNC`로 만든 인덱스는 빌드가 끝나기 전부터 `pg_indexes`에 보였습니다. `pg_index.indisvalid`가 참이 될 때까지 기다리도록 도구를 고쳤습니다.
- **일시 오류:** 적재 중 `XX000 server unavailable`이 발생해 재시도 대상에 추가했습니다. 트랜잭션당 3,000행 한도에 맞춰 적재와 삭제를 나눴습니다.
- **연결 관리:** DSQL 연결은 1시간 한도가 있어 50분마다 다시 연결했고, IAM 토큰은 10분 캐시했습니다.

## 결론과 한계

- **지연:** 1600 TPS까지 DSQL은 SLO를 여유 있게 지켰지만, 쓰기 지연이 Aurora Serverless v2보다 약 6배, 읽기 지연이 약 4배 길었습니다. DSQL의 지연은 도착률에 거의 영향을 받지 않았습니다.
- **처리량:** 연결 16개 기준으로 DSQL의 처리량은 대조군의 약 1/3–1/6이었습니다. 이는 지연 차이에서 나온 값이며 DSQL의 용량 한계를 뜻하지 않습니다.
- **측정하지 못한 것:** DSQL의 SLO 용량, 기준 처리량(Qref), 공통 도착률 비교(본 측정), 경계 탐색, 반복 간 편차.
- **한계:** 모든 셀은 1회 실행입니다. 러너 사양이 단계마다 다르고(파일럿 `c7g.4xlarge`, 탐색 `c6g.4xlarge`), DSQL은 퍼블릭 엔드포인트, 대조군은 VPC 내부 경로입니다.
- **재측정 과제:**
  - 초기화를 여러 연결로 병렬 실행하거나, 셀마다 새 데이터 영역을 쓰도록 바꿔 DSQL 대량 삭제 병목을 피합니다.
  - Spot 회수에 대비해 여러 인스턴스 타입을 허용합니다.
  - 파일럿 뒤 결정 대기 중 유휴 비용을 줄이도록 순서를 조정합니다.
